# Owner provisioning of local MCP runtimes

The owner selects name, logical agentId/serviceId, exact conversationIds, read_inbox/send_message actions, expiration and maxDataBytes. ProvisionRuntimeRequest also requires an operationId (1..128 bytes, no control characters); it accepts no principal, seed, filesystem path, executable or owner token. The core generates a random runtime signing key. Registry grant and encrypted provisioning record commit atomically in SQLCipher, reusing grant validation/signing. Namespace authorization/provision/<hash-of-operation-id> stores the finite approved intent and scoped seed; it is not exposed through renderer snapshots or agent methods.

An identical operation retries the same seed/grant without state changes, including after daemon restart. A different intent under the same operation ID fails. Revoked/expired grants cannot be reprovisioned through an old operation. Different operations create distinct runtime keys while preserving the supplied logical agent/service identity. ProvisionedRuntime is an internal non-serializable material object with zeroizing seed, grant and ownership epoch. RuntimeInfo is owner-readable public metadata: grantId, name, principal, agentId, serviceId, conversationIds, actions, expiresAt, maxDataBytes, and status active/expired/revoked. Revoke remains the existing broker operation.

Owner-only daemon commands provision_runtime and list_runtimes expose this service. The daemon materializes the seed in a bounded private MCP credentials file under <canonical-profile-parent>/runtimes/<grant-id>.json, with 0700 directory and 0600 regular file, no directory symlink or shared directory. It returns public runtime metadata, credentialsPath and ready mcpConfig containing mcpServers entries (command = bundled sibling agentic-mcp, args = --credentials plus fixed path). No caller chooses the output path or command. No secret appears in owner response, snapshot, logs or config.

The encrypted core is authoritative. Credentials materialization failure reports failure while the registered runtime remains listed and revocable. Retrying the same operation after fixing local I/O recreates the same credentials; it never creates a second grant or silently replaces a shared directory. Revoke denies copied credentials even across daemon restart. Runtime key file is intentionally readable by this local MCP process; root/master credentials remain unavailable to it.

Tests precede implementation: core MLS usage, idempotent provisioning and exact restart, changed-intent rejection, independent keys, expiry/revoke, real SQL rollback; daemon-to-MCP config must work against an actual peer, keep keys off public results, survive missing credentials/restart, reject owner authority from signed agents and recover from a failed file materialization. Native commands/UI and packaging integrate next; this primitive alone does not complete runtime management or V1.
