# Proposed next module: owned postage preparation (not implemented or accepted)

AppCore prepares an opaque local proving request from an already finalized custody
mark. The public API accepts an existing operation/intent ID, ticket index, desired
operation digest, expected current checkpoint ID, expected common checkpoint ID,
a fresh funding proof at that common root, current registry proof and an explicit
finite statement interval. It does not accept issuer/network/registry profiles,
private seed/salt or a caller-selected funding root.

Core chooses the latest retained authenticated checkpoint strictly before the
intent's fixed beacon block. Require it to match expected_common_checkpoint_id;
an older per-deposit checkpoint with an otherwise genuine membership proof must
not be used. Reuse Archive's authenticated entries through a small private query,
then the existing verify_custody_funding path for original and common funding.
Both proven leaves/count/class/expiry must agree, original bound rows are immutable,
and the common registry epoch/root must match the persisted private intent.

Derive issuer domain/code hash, registry domain/epoch/root, selected funding root
and network from trusted Core state/opaque validation outputs. Require interval
start at or after the common checkpoint issue, start <= actual caller clock < end,
and end <= funded expiry and registry snapshot admission end. It may outlive the
current checkpoint lease only as a local relation request: no preparation is a
current admission capability. The runtime must reauthenticate after proving.
The product controller still needs a common interval policy; this trusted local
Rust API must not be exposed as arbitrary remote spend/context authority.

Use agentic-postage-proof's existing context, witness and evaluator; no new crypto
or duplicate statement implementation. PreparedPostage has no Deserialize, Serialize,
Debug or Clone. Its public getters expose only context and nullifier. Consuming it
releases a Zeroizing<Vec<u8>> containing the strict existing {context,witness} CLI
request for a trusted local supervisor's stdin. Serialize directly from borrowed
typed fields, not a serde_json::Value containing extra copies of the private seed.

Require the existing durable monotonic clock commit before releasing the request.
Errors leave funded/intent rows unchanged, including SQL commit failures and corrupt
persisted evidence. Fresh caller proofs must not silently heal corrupt saved rows.
Dropping/cancelling an in-memory preparation and reopening SQLCipher recovers the
same mark and nullifier; no prepared/spent record or proof file is created.

Test corpus: `crates/core/tests/fixtures/postage-wallet.json`, generated by
actual Anvil payments in `crates/core/tests/fixtures/generate_postage.py`. Two chains each contain a real
individual original funding root, a later common pre-beacon root after a second
owner's paid purchase, consecutive independent signed history and Python CBOR/HMAC
expected outputs for all four funded tickets. Original and common roots pass the
existing actual Rust custody CLI; swapped membership proofs reject. Short-head
expiry and renewal with genuinely changed registry proof also pass (16 checks).
These are public deterministic test seeds and historical clocks, not anonymity or
live runtime evidence. Separate shared-root random-owner proving evidence is retained
under evidence/reviews/P02-shared-root.

Required tests before code: unbound/fresh wrong owner rejected; all paid indices
match independent complete journals; proof targets the later common root while the
original funded row stays byte-for-byte; out-of-range ticket/unknown or older common
root/genuine mismatched proof rejected with positive controls; restart/drop preserves
exact request/nullifiers; renewed head requires fresh registry evidence and preserves
same common statement; actual clock/interval boundaries and SQL failures fail closed;
corrupt funded storage is not healed by valid current input.

Remaining integration after this module: retained-anchor policy beyond bounded
history eviction; full daemon supervision including parent death; real interrupted
proving and successful retry from encrypted funded state; fresh-authority receipt
verification; native packaging/UI and Linux guest tooling; canonical P03 spend.
This proposed preparation API does not complete any of those later requirements.

The five test functions in `crates/core/tests/support/custody_postage.rs` reuse
the existing custody-owner SQLCipher helpers. The compile RED is missing new
Core types/method and its existing local postage-proof dependency; no production
implementation or Cargo changes have been applied. An earlier fixture-construction
run failed because Anvil mined equal timestamps for the individual and common
roots. The fixture now explicitly advances the next block after the first payment
and asserts strict timestamp/block ordering before signing; actual CLI compatibility
then passes. That fixture failure is not the production API RED.

The first critic returned REVISE for a non-isolated statement-expiry check. It now
uses a nonempty short window ending strictly before checkpoint, registry and paid
expiry: end-1 succeeds, end rejects, and the longer context succeeds at the same
end time. An unused opaque handle is explicitly dropped before serialization and
its retry/unchanged persisted rows are checked. Production code remains untouched
pending the next critic verdict.
