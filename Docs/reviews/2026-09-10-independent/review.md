# Agentic Internet V1: independent architecture review

**Snapshot:** September 10, 2026 · `implementation/v1` · `eea229c4850235a22d28a5ddc60208e62a60ee46`  
**Current acceptance subject:** `v1-code-and-testnet`, 67 cards, 22 E2E, macOS arm64 / Windows x86_64 / Linux x86_64.  
**Verdict:** continue with simplifications and **surgically redesign the spending, queue, and storage lifecycle**. Do not rewrite P2P, MLS, and the transactional Core.

This is a review of code and development direction, not a cryptographic certification, a pentest, or a new full release gate. Paths refer to the archive's `project/`; line numbers refer to the specified snapshot. Test and evidence package names are given for reproducibility, not as a claim that they were re-executed. The full log of my own checks is described in section 7.

## 1. Verdict for the owner

### Development is going in a reasonable direction, but the sequence of work must change

**The foundation does not look wrong.** There is already a real Tauri → daemon → shared Core → SQLCipher/OpenMLS → authenticated network path; scoped MCP passes through the same authority control. Not only data structures are implemented: there are real SQL transactions, processes, Noise connections, on-chain funding proofs, finalized spends, holder obligations, and retrieval of ciphertext without a running sender. Moving the new sender path from ZK to a signed public book is a useful simplification. E2EE and the finiteness of the paid resource remain, and the per-operation prover, unnecessary for the current anonymity promise, disappears. Basis: `crates/core/src/lib.rs`, `crates/store/src/lib.rs`, `crates/node/src/{runtime,mcp,public_sender}.rs`, the previous `evidence/reviews/P02-public-sender-daemon/` package.

**But the application is not yet close to completion under the current 67/22.** The reason is not the number of tests or crates. Key mechanisms are proven on short fragments of life, while the long user cycle connecting them is missing: finish a queue, survive a committee change, discover the whole history across different holder sets, restore copies without clients, recover secret state after device loss. In parallel, simple product entry points are not finished enough: the CLI skill, the graphical book/payment, groups, Windows. These gaps cannot be closed by the next good backend library without an integration priority change.

**There are blocking problems.** I did not find a confirmed cryptographic break or a successful double-spend in the limited path read. However, direct limitations incompatible with ordinary prolonged use were found. Therefore the wording «no critical issues, only the interface remains» would be wrong.

### Five main decisions

**1. Make the transport long-lived instead of increasing the demo size.** In `postage-spend/src/lib.rs:123–156,191–239` a new spend is only allowed in epoch 1, the next element requires the full prefix, and after 128 records `Limit` is returned. Independently of this, `core/src/public_sender.rs:332–359` caps at 128 active jobs; terminal retirement was not found. These are two different limits: the issuer-global journal and the local queue. We need a persistent spent set, bounded proofs/snapshots, and handover without resetting one-time-ness; for the queue — terminal transitions, accounting, and ready-to-run tasks. Simply changing 128 to a larger number is not a sufficient fix.

**2. Finish storage as a user promise.** The new paid-index store protects an individual record well, but it is not yet a network index of history. The old sender searches for the intersection of message holders; with disjoint rosters it is empty. There is no autonomous 10→7→10: there are real but owner-requested copies. The existing successful sender E2E proves two stored messages in an established conversation, not long history, book changes, the first Welcome, and self-driven repair. The next main result should be exactly a complete offline/recovery scenario, not another form of receipt.

**3. Preserve decentralization, but name the trust honestly.** No mandatory central message server was found in the path read. Bootstrap/relay/operators can be configured independently. However, the L2-checkpoint model trusts a threshold of pre-pinned attestors; this is not a light client. A registry of bonded keys and twenty processes on localhost do not establish operator independence. Only the roles, keys, configurations, access to funds, and data actually available outside its control survive the company's closure. An operational check of this matters more than increasing the number of local validators. Detailed boundaries — section 5.2.

**4. Return speed and finished interfaces to the center of development.** The scheduled worker processes one job every 500 ms. At 128 jobs the interval between its passes over one job is at least 64 seconds, before processing costs. This is a calculation from code, not measured network latency; network callbacks may arrive between passes. In addition, heavy verification/SQL/full serialization of MLS state sit in synchronous sections of the network runtime. Before a new overall economic subsystem, it is more useful to fix these structures, surface the real stages in UI/CLI/MCP, and measure p95/p99 on long history. `delivered` and `stored` must remain different facts.

**5. Remove the obviously unnecessary from standard V1.** The default desktop build still builds and packages ZK sidecars. JobsPanel and jobs MCP methods are active although orders are deferred. These are real isolation candidates, unlike MLS, grants, once-spend, indexes, and repair. Separately, renegotiate the eight provider integrations and the full subsidy/royalty/settlement onboarding: they are still in scope and greatly expand the release. Deferring them is allowed only with an explicit change of user entry and economic guarantees.

### These are not «unnecessary edge cases»

In the original thread it was the owner who asked for ten nodes and self-driven copy recovery, groups, first launch without an own server, bounded stamps, and agent operation. These are not the assistant's later fantasies. The genuine ordinary failures here are a switched-off sender, a lost laptop, dead holders, a network address change, duplicate retry, and network partition. Removing their handling means changing the product.

At the same time the **specific way** of handling it was not specified by the owner: ZK, full ancestry at every step, duplicating portable evidence, several inconsistent status stores, mandatory development of all identity providers before a working messenger do not become necessary just because they are described in detail. These decisions must be evaluated by their benefit in V1, not by the strictness of their documentation.

**Decision to continue: yes. Decision on the current pace of «one more small protocol module»: no.** A transition to a finished vertical with a long lifecycle, honest statuses, measurements, and the sender/company disappearing in the test is needed. This is a targeted rework of several bottlenecks, not a reason to throw away the foundation built.

## 4. Implementation matrix: all 67 cards and all 22 E2E

### How to read the classification

«Implemented» means that a complete mechanism within the card's subject was found, not that the current revision passed all platform checks. «Partial» means substantial code with an unfinished vertical/guarantee. «Designed only» — a concrete plan exists, no ready target path was found. «Missing» and «Insufficient evidence» are not used automatically instead of planned: the absence of code was checked against the tree, dependencies, and entry points, not by backlog labels.

The assessment follows the current `release-scope.json`, including overrides. Old dependencies on V2 in the original backlog are not current release dependencies. Individual tasks inside a partial card may be fully missing: for example, the standalone CLI in M06, although stdio MCP already works. The presence of V2 order implementations is not counted as messenger attachments or groups.

This is **not a readiness percentage**: one partial handover or recovery card may be worth more than several finished adapters. E2E are classified by the whole user scenario, not by the presence of a same-named test file.

A01–A06, Q01–Q06, M03, M04, M07, U08 and X07 — 17 deferred cards. E12, E13, E15, E16 — deferred scenarios. These are not V1 defects. On the contrary, the active JobsPanel/tools are a reason to isolate the scope leak while keeping existing regression tests and historical data compatibility.

## 5. Minimally sufficient target V1 architecture

### 5.1. User, promise and threat model

The V1 user is a person with a local desktop profile or an agent to whom this person has granted limited authority. They exchange private and group encrypted messages, later receive what was missed, manage devices and agent permissions. They pay not for «the truth of a message» but for a finite network/disk resource: volume, retention period, required copies and conditional repair. Book payment and local E2EE identity are different entities. Free onboarding is spending a sponsor's funds, not free infinite load.

In the original `Docs/ideation agentic internet/messages.json` the User messages were read separately. Ten replicas and autonomous repair, the absence of mandatory organization servers, groups and agent communication are owner requirements. Specific ZK/consensus constructions and research estimates in Assistant messages were not taken as user requirements. A later explicit decision to defer orders/rating was applied on top of the early wishes of a future economy.

| Threat or failure | Minimally necessary mechanism | What is not a mandatory consequence |
| --- | --- | --- |
| A foreign relay/storage reads content | MLS/E2EE, keys with participants, authenticated ciphertext | Payer anonymity, ZK for every spend, IP hiding |
| An agent spends someone else's budget/access | Capability chain, principal scope, revocation, atomic budgets, original-grant recheck | A full DeFi platform; OS sandbox automatically from MCP |
| Retry, competing spends of one stamp | Stable ticket ID, single spend authority, durable once-spend state | An L2 transaction per message; global ordering of all plaintext messages |
| The sender disappeared after confirming storage | Independent holders, verifiable locations/index, available control history and secrets with the recipient | A permanently online sender; a link only to its last memory |
| Three holders died, both clients offline | Operator anti-entropy, bounded replacement authority/resources, repair of data and index | A separate centralized repair coordinator; infinite copies without a budget |
| The last laptop is lost | An agreed backup/rejoin and an explicit policy for restoring secrets/history | The ability to decrypt ciphertext from public identity alone |
| Partition, committee change, old proofs | Quorum safety, monotonic authority, non-resetting handover, historical verification | A promise to finalize in any part of the network; lowering the quorum for availability |
| The company closed | Independent roles/keys/funding/config distribution, offline installers/source, alternative bootstrap | The sufficiency of twenty processes with different keys on one host |

A reasonable base V1 model: an operator can lie, delete data and disappear; the transport does not see plaintext; the number of Byzantine consensus participants is bounded by an explicitly adopted model; the user endpoint is not compromised; keys and recovery have a defined policy. Availability requires live honest sources, a network, an unexpired obligation and resources. No cryptographic receipt guarantees physical preservation after the death of all copies.

### 5.2. Where the network is decentralized and where it keeps trust

| Role | What is implemented | What happens without the organization | Missing proof/condition |
| --- | --- | --- | --- |
| Bootstrap | Explicit independent peers/invites, bounded bootstrap set; no mandatory vendor default; opt-in LAN | Old reachable peers and alternative addresses allow entry; from an absolute zero of addresses the network is not discoverable | Cold join without vendor DNS/API, distribution of addresses and trust config through an independent channel |
| Discovery/DHT | Partial routing tables, authenticated records, configurable server roles | Works while independent DHT/operator nodes are alive | A volatile DHT locator cannot be equated to durable complete history; expiry/refresh/anti-replay and book continuity are needed |
| NAT/relay | Real libp2p NAT/relay paths and tests | Possible with independent reachable relay providers | External reachability, capacity and their operation are needed; a local NAT fixture does not cover the internet |
| Registry | Funded/bonded operator units, sealed snapshots and membership proofs | Contracts/data can live independently of the developer | Stake units do not prove different companies/disks/providers; randomness uses a blockhash with recognized producer bias |
| L2/RPC | EVM funding/state proofs relative to the accepted root | The RPC can be changed if there is access to the chain and authenticated checkpoints | A state proof does not establish the canonical finalized chain by itself |
| Checkpoint attestors | Pinned profile, signer threshold, sequence/previous hash/lease and durable fences | Available independent signers extend the trusted window; otherwise new admissions end at the lease | Who controls the keys and distributes the profile; which L2 finality and reorg model is adopted |
| Spend finalizers | A real P256 quorum engine and the shared issuer spend domain | A live independent quorum can finalize under the acting authority | Epoch 1/128 currently limit continuation; different roles must not be mistakenly counted as one trusted service |
| Data/index holders | Authenticated custody/paid index backend, grants, quotas, receipts | Stored historical obligations can be verified and read while routes/copies are available | No full network-index and autonomous repair; expiration of a new admission must not delete still-active old obligations |
| Payouts and maintenance | Funding exists; full settlement is not finished | The protocol itself does not pay for electricity to volunteer operators | A transport reward/reserve or an honestly bounded sponsored testnet is needed |

`spec/postage/trusted-checkpoints.md` directly defines a trusted model. A threshold signs a root bound to the network/issuer/registry/profile. Verifying EVM membership relative to the root and verifying that the root is really finalized in L2 are two different guarantees. If a threshold of trusted signers asserts a false root, the current model accepts it. This may be acceptable for an explicitly federated testnet, but it does not match the promise «we trust no one».

The absence of a built-in mandatory company key is a plus. But manual profile pinning does not disappear as a problem: a new user must obtain it securely and have a way to continue after an epoch/operator change. A quorum/key profile change must not create a second acting spent ledger for the same funds. Snapshot/issuer policy binding must not be bypassed by hot replacement for convenience.

When the organization disappears, different outcomes are possible and they must not be mixed. Already-familiar online peers can message each other directly. Old local history remains local. Paid retrieval is possible if ciphertext, index/control metadata, secrets and historical trust evidence survive. New spends are allowed only while funding/authority/lease act and a quorum is available. After the window expires, new financially backed promises should stop, rather than declaring data already delivered or erasing old active obligations.

### 5.3. Why an issuer-global spend log is needed and what to do with it

The book owner's signature proves that they authorized a spend, but does not prevent them from signing two contradictory spends of one ticket. Ten holders can see different halves of the race. While one paid unit must produce **one** canonical obligation, independent accepting parties need a common answer «this ticket is already bound to this operation». This justifies the spent set and coordination. A signature without coordination or without a pre-assigned single authority does not give the same guarantee.

The current code uses `postage/spent/{issuer}/{nullifier}`. In the new public scheme the ticket/nullifier depends on the issuer domain, the book commitment and the stamp index, and does not change with the operation. This is the right property. First funding/context/signature is verified, then the record is coordinated; QC confirms this coordinated record. After that an individual holder accepts the final obligation under its own placement/consent/bytes/TTL rules and signs a receipt after a durable commit. QC does not prove ten physical copies, and ten receipts are not confirmation of a read by the recipient.

For the classic case N=3f+1 and quorum q=2f+1 two conflicting finalizations intersect in an honest participant under the model's constraints. In the general case 2q−N>f is required; for progress without Byzantine participants q≤N−f is also needed. Progress requires a sufficient number of available participants and suitable network conditions; a partition may legitimately stop the system. For the Commonware Simplex family used, the documentation separately emphasizes the role of application validation and its own durable journal. A ready engine does not automatically implement the correct transfer of the application's spent state [W2].

**The current problem is not that a ledger exists, but its representation and lifetime.** Full ancestry to genesis plus a hard bound of 128 does not let a constantly working issuer continue. `HandoverRequired` at epoch !=1 is an honest fail-closed, but an unimplemented handover. A correct transition must preserve finalization locks, the proven last state/snapshot, the global spent set and the boundary of old authorities. Loading an empty new journal with a new epoch number is unacceptable.

| Option | Guarantees | Complexity/operation | Migration and recommendation |
| --- | --- | --- | --- |
| **A. One issuer-global journal, indexed spent set, authenticated snapshots** | Preserves the current global one-time-ness; under partition it stops new finalizations without losing safety | Does not require new committees per book. The hot issuer remains the unit of availability/load. Bounded proofs and batching are acceptable after measurement | Minimal protocol migration, but serious lifecycle work. **I recommend for V1** |
| **B. Canonical book/bucket partitions with a single authority for a ticket** | Can preserve the same one-time-ness if the partition is assigned immutably, the state transfer is single, old authorities are retired | Fewer shared hot spots, but more committees, routing/state transfer and partial failures. By itself this is not a simpler first release | An allocation version and a proven bridge from the old journal without dual authority are needed. Defer until measured necessity |
| **C. Vouchers pre-bound to specific providers** | Can locally bound each provider's resource without a shared order of all spends. But the former atomic semantics of one spend for a full R10 obligation and free re-addressing are not preserved automatically | Simpler acceptance at a specific node; harder partial purchase, replacement of dead providers, refunds and repair funding | A genuinely different product contract. Only an owner-approved change, not a drop-in simplification of the current V1 |
| **D. Every spend in L2** | One-time-ness is delegated to the chain under accepted finality | Less own off-chain consensus, but the latency/cost/availability of every operation depends on L2 | Contradicts the adopted boundary «no L2 transaction per message» and bounded autonomy. I do not recommend it for the current scope |

Hence I do not see an option «keep exactly the same guarantees but completely remove coordination». The simpler solution **within the same guarantees** is one understandable journal with indexed state and bounded snapshots, not a full prefix in every proof and not a new network of shard committees before a benchmark.

The committee size should be justified by threats and deployment, not by the number of processes that could be launched. For a small testnet, several truly independent operators and failure verification are more useful than dozens of keys of one owner. This does not mean an equivalent attack budget or permissionless Sybil resistance: the assumptions must be stated. The heavy 64-validator/R24 gate was not run by this review and by itself does not remove this question.

### 5.5. End-to-end delivery and what each status means

**UI path in the snapshot.** `ChatShell.tsx:29–37` keeps the request UUID for retry → `desktop-api.ts` → Tauri `send_message` (`src-tauri/src/lib.rs:166–172`, with `owner_window`) → `DesktopBridge::request` (`desktop-host/src/lib.rs:239–240`) → daemon dispatch (`node/src/runtime.rs:1076–1095`) → `AppCore::send_message` (`core/src/lib.rs:434–545`). Core prepares the MLS ciphertext and the signed packet; `commit_outgoing_with_retry_states` binds the MLS state, message, outbox, operation and public sender reservation in one SQL transaction. After the commit, «accepted locally» is a valid success, not «10 copies stored».

The daemon pump (`node/src/runtime.rs:645–700`) processes the direct outbox and the public sender. The public sender prepares public postage, obtains the spend record/QC, sends custody puts, checks receipts and publishes the locator. After the initial owner policy setup this is indeed an automatic send: the old live report records zero owner work/retrieval calls during the ordinary workflow. But wallet/issuer/sponsor setup is done with internal owner commands; there is no user purchase/bind/status UI. Therefore the library wallet API cannot be counted as a graphical function.

The recipient verifies the network peer, the signed packet and the author's membership in the group, then decrypts. `receive_application` (`core/src/lib.rs:653–706`) saves the crypto/message/completion state and **only then** signs the ACK. `receive_receipt` (`708–723`) checks membership among the original own messages and the conversation root before completing the direct outbox. This is the correct transactional boundary to preserve.

**MCP path.** `agentic-mcp` accepts a stdio tool call; `node/src/mcp.rs:177–205` forms a signed broker call. `core/src/broker.rs:378–408` checks the grant registry, root/ownership epoch, nonce and current state fences. `messages.send` (`501–529`) computes the principal-scoped operation, checks contact/data limits/budget and uses the common authorized send. `inbox.poll` returns a prepared page only after committing cursor/lease/operation; `ack` verifies the canonical lease token, owner and expiry. A duplicate «lightweight agent Core» bypassing policy was not found.

The original runtime grant is rechecked before executing deferred paid work (`core/src/public_sender_execution.rs:42–103`), not only at enqueue time. This protects the revoke-between-prepare-and-send scenario. But an external agent is still obliged to design side effects as at-least-once: an idempotent messaging operation and an ACK inbox do not make an arbitrary external call exactly-once.

**The CLI path cannot be traced to the end because it does not exist.** The main node CLI can `Serve`; the verifier/operator/proof CLIs do not replace the user's `identity/send/delivery/poll/ack`. Another thin adapter to the same daemon API is needed, not a separate policy and not a mandatory MCP wrapper.

| Fact | Proof | What can be shown to the user | What it does not prove |
| --- | --- | --- | --- |
| Local accepted | Commit of message + MLS state + operation + queue | «Accepted on this device» | Payment, network delivery, storage outside the device |
| Book funded / reservation | Verified funding and an atomic local reservation | «There is budget / the stamp is reserved» | A canonical spend; a reservation is not an irreversible spend |
| Spend finalized | A valid QC on the exact ticket/operation/context | «The spend is confirmed» | Receipt of the ciphertext by holders |
| Custody committed | N authenticated receipts on the exact object/TTL/placement | «Stored N of 10; until …» | Current physical presence at all later moments |
| Index accepted | A receipt on the descriptor and verified holder locations | «Published for later lookup» | The completeness of all pages/books/epochs of history |
| Recipient received | A signed ACK after the recipient Core commit | «Delivered to the recipient» | The user has read it; ten copies already exist |
| Read | An explicit corresponding event from the recipient | «Read», if the function is implemented and enabled | Cannot be derived from a retrieval/storage ACK |
| Durable health | Recent actual retrieval/inspection and repair state | «10 verified … / 7 available / recovering» | An indefinite guarantee after TTL or the death of all sources |

UI/CLI/MCP must read one persisted projection of facts, with operation ID and an explainable error. Independent «delivery» and «storage reliability» axes are needed: «delivered, while stored 4/10» is quite acceptable. A network timeout after a request is «outcome unknown, checking», not an automatic refund or a repeated allocation of another ticket. A cancel after finalization also does not return the already spent right without an explicit protocol.

### 5.6. Indexes, history completeness and R10

**A logical index is justified.** Ciphertext with ten unknown addresses is useless to a returning offline client. A DHT record is a short-lived locator, not sufficient proof that the whole range of messages has been found. A roster per book reasonably stabilizes metadata placement and reduces dependence on which data holders were chosen for each message. But the roster itself does not solve the search for previous books, epoch change and decryption of old MLS messages.

Importantly, the new scheme **does not introduce a second stamp per index**: `spec/paid-index-store-v1.md` defines a bounded entitlement to a compact index entry in the same paid operation. Data and index have separate logical obligations/quotas but do not require a second global spend transaction. What can be simplified is representation and operation, not the removal of a nonexistent «double payment».

The minimal chain should look like this:

```text
the source signed ciphertext and the exact operation
  → verified public funding + a single SpendRecord/QC
  → data custody receipts with authentic operator/transport/position/TTL
  → descriptor + verified holder locations
      [cross-check against the same spend/QC, object hash, class, book, expiry]
  → durable index put onto the assigned book/epoch roster
  → authenticated index receipt kept by the sender/operator
  → an independent locator/manifest of the chain of books and epochs
  → bounded pages distinguishing gap / expired / unavailable / complete-range
  → fetch the exact ciphertext from valid holders
  → ciphertext/control sequence verification and the ordinary recipient Core commit
  → recipient ACK, separate from the index/storage receipt
```

**Completeness requires a scope definition.** A quorum receipt on one descriptor does not prove the absence of other messages. An empty page from one node does not prove the end of history. A signed high-water mark/manifest can fix the completeness of the *published and accepted range*, but not the existence of never-published messages in the sender's head. The committed sequence space, gaps/tombstones/expiry markers, book linkage and authenticated termination of each range must be defined. A durable cursor must not silently advance on an unavailable node's answer and forget a hole.

The incoming Core must survive repeats, out-of-order delivery and partial pages. For MLS the correct control history is required first; simply applying all new epochs and then reading old application ciphertext is dangerous under bounded key retention. The first Welcome requires a separate initial rendezvous capability, since an exporter of an established conversation does not yet exist. On the client's return after a cold restart, operations continue from SQL, not only from the in-memory Work.view and the cached route intersection.

**A practical R10 test.** Data/index operators are launched with separate durable directories, explicitly described organizations/failure domains and spare capacity. A message is accepted on ten data holders; the actual bytes are checked, not only signatures. Then both clients are switched off. Three chosen holders lose exactly disks/data and are unavailable, not merely return a different metric. The surviving operator loops independently notice the deficit, verify the remaining sources, use the pre-bounded replacement permissions and repair reserve, transfer ciphertext to spare nodes, record receipts and update discoverable locations/indexes. After the recipient's cold restart and with the sender still off, it receives the entire expected history.

Negative outcomes are also needed: no spare capacity; not enough budget; a source lies; TTL expired; an old committee lease; a partition between holders/indexers; a duplicate repair; all ten copies die. The system must show degraded/unavailable/expired, not a fictitious ten. It is not obliged to magically restore data when no live copy exists. If the requirement «exactly ten at every moment even under partition» implies a ban on brief over-replication, the owner should clarify it: a bounded temporary excess is safer than deleting a copy on the suspicion that another still exists.

**A separate consensus per repair ACK is not needed.** What is needed are verifiable rights to bounded replacement positions, an immutable original obligation/TTL, correct accounting and stable dedup. This can live in one custody store/repair scheduler. The chain «a receipt proves a receipt» must not be extended indefinitely: portable original evidence and a short verifiable binding of a new copy to it are simpler for a cold restart.

| Index option | Guarantees and benefit | Cost/drawback |
| --- | --- | --- |
| **A separate logical book index roster + per-message data placement** | Does not require the intersection of all data rosters, a separately paid bounded metadata resource is already described; data placement is flexible | Book/epoch discoverability, location cross-check and self-driven index repair must be kept; additional logical receipts |
| **Colocation of all book data and its index on one book roster** | Fewer moving locations and simpler lookup; the same processes/tables can be reused | Hot books and concentrated failures, less flexible volume distribution, harder large book migration; the former placement guarantees change |

For the current snapshot the first option with a **shared physical store, proof cache and scheduler** is preferable, without a new service per object type. The second model is realistic, but it cannot be declared a free simplification with the same failure-domain and load-balancing properties.

### 5.7. Cryptography and legacy isolation

OpenMLS is a suitable foundation, not a reason to rewrite. The project uses ready MLS key establishment/ratchets and verifies that the decrypted author matches identity. MLS itself defines message protection and group state changes, but assumes a separate delivery service; it is not a durable storage protocol or automatic delivery of all control messages. Therefore the absence of group/offline integration cannot be justified by the presence of the library [W1, W3].

The dangerous places are at protocol junctions: binding a transport key to an operator identity; which root may act in an epoch; in what order membership commits are applied; after which commit an ACK is allowed; which exact object/QC the holder signed. Own domain-separated structures are justified here because they express the paid resource and the application's authorities, which MLS does not define. But they need short verifiable specifications and independent negative tests, not new cryptographic primitives without need.

In public postage the outer book commitment uses a separate domain. Ticket identity fixes issuer/book/index; the signature binds the journal, funding leaf/count, validUntil and the paid amount. The format is determined strictly: malformed public bytes must not switch the verifier to a permissive legacy path. In the `verification.rs` read this boundary is respected. The new public funding slot and the legacy slot are not just two names of one balance; they cannot be «merged» by a migration without preserving global spent identity and accounting.

**Privacy:** E2EE protects content from transport operators, but does not make public postage anonymous. Book/funding/key/ticket and the spend are linkable; the metadata index/roster, size, TTL, endpoints and time give additional linkage. Outer documents/transport identities can reveal more than the inner MLS ciphertext. This is an acceptable new boundary if the UI/docs describe it directly. The old ZK-anonymity promises must not be carried over into public V1.

**ZK isolation must be migrational, not a deletion.** Proposed order:

1. Freeze the legacy guest source/dependencies/image ID and regression vectors. Do not accidentally change the image ID when moving shared types.
2. Extract neutral native funding/statement/authority types that currently pull `postage-proof` into the public Core. One feature at the top UI does not break the lower mandatory dependency.
3. Split `legacy-zk-verify` and `legacy-zk-prove`; the new public V1 does not need prover sidecars. Old historical obligations must remain verifiable and accessible without locally running a new prover.
4. If really unspent legacy private books exist, define a supported compatible spend path or an explicit funded migration. In all cases — the same issuer-global spent set, without a new right to already spent funds.
5. Move legacy proof builds/regressions to a separate target/possibly a separate workspace. `default-members` by itself does not exclude heavy members from `cargo test --workspace`; the ordinary V1 gate must choose the corresponding target explicitly.

`postage-zk/build.rs` unconditionally calls `embed_methods`, and the standard desktop script runs a separate proof build and sidecar packaging. Therefore removing them from the critical path is a real current win in toolchain complexity. Clean build size and time before/after were not measured; preserved incremental author build times are not suitable for promising a numerical speedup.

### 5.8. Performance and limits: measured separately from assumed

| Observation | Type of knowledge | What follows from it |
| --- | --- | --- |
| One job per scheduled pass every 500 ms | Direct code `node/public_sender.rs:86–121` | At 128 jobs the scheduled cycle is ≥64 s; this is not a universal 2 messages/s limit and not a WAN benchmark |
| Full-prefix spend, limit of 128; epoch 1 | Direct code | No lifetime continuity, prefix cost grows; a new shared issuer quickly hits the limit |
| Custody/index limits up to 128 objects and 8 MiB, full JSON state | Direct code `custody.rs`, `index/storage.rs` | A bounded demo store is not ready for long shared operator workload; raising the constant does not remove scan/write amplification |
| Two serialized full portable index fixture objects together >262144 bytes | Direct assert `paid_index.rs:600–603` | Descriptor compactness is not the compactness of complete evidence; this is not the average production index size |
| MLS prepare restores the provider, dump serializes all entries | Direct code `crypto/lib.rs:104–113,449–493` | Work depends on state size; incremental storage and tail latency measurement are needed |
| 164 ms public message preparation in one previous successful live trace | A preserved author measurement of one step/environment | Proves that preparation without ZK is possible; does not characterize the full send/QC/10 copies/index/receive and not WAN p95 |
| 10 receipts per message in a two-message local EVM/daemon run | A preserved integration result | Real baseline storage execution, not sustained throughput and not independence of failure domains |
| WAN latency, steady-state TPS, repair cost, CPU/byte and clean multi-OS build | Not measured in this review | Production speed/cost cannot be promised from the number of tests or the type of cryptography |

What should be measured separately: local accept→commit; direct recipient ACK; spend finalization; receipt #1/#10; index publication; offline lookup/page/decrypt; time-to-repair; queue/retries; CPU and event-loop stalls; evidence size on the wire; disk writes and memory. Compare on one revision, one workload and with stated RTT/loss/operator locations. The long test must cross the current 128 and several authority epochs, not bypass the limit with a new issuer for every short run.

For storing proof bundles, content-addressed dedup and a cache of verification results of unchanged bytes are useful, but fresh authority/grant/expiry/fence checks must remain at admission/commit. A CPU worker returns a proven immutable result; only Core rechecks the current rights and commits. This preserves safety without blocking the network loop. Fully scattering the mutable Core across parallel tasks for speed is a bad simplification.

P256 quorum certificates grow with the number of signatures; threshold aggregation can reduce them but brings key generation/resharing and operational conditions. At this stage it is more reasonable to eliminate full evidence/JSON duplication and unnecessary sequential waits than to add DKG for a not-yet-measured bottleneck. This agrees with the described Commonware signing scheme options [W2].

### 5.9. Agent and WebView isolation

Tauri command manifests/capabilities and `owner_window` are used correctly: what must be checked are the actually registered commands, not the assumption that any custom commands are automatically restricted. The Tauri documentation explicitly distinguishes the WebView capability boundary from the trusted Rust/application layer [W4]. The project has an explicit manifest, so the common warning «all commands are open in Tauri» is not a found defect here.

Runtime credentials include the seed in a 0600 file inside a 0700 directory. This is meaningful for passing a separate grant to a trusted process/host. It is not a sandbox against arbitrary code with the same OS UID and unrestricted filesystem. Protection from such an agent requires a different OS boundary: a separate UID/sandbox, a restricted mount and a single delegated channel. In V1 it is possible to officially support a tool-constrained host and not build an own VM manager; one cannot simultaneously promise isolation from an unrestricted coding agent on the same account.

Inbox leases and outbox fencing are needed already in V1, not for future jobs. It is useful to simplify the storage lifecycle: a single retention/GC policy for nonces, poll operations, lease indices and terminal sender states, with sufficiently long dedup windows. Too-early cleanup revives a repeated side effect; indefinite retention of every ACK/POLL creates another resource limit. The full lifetime GC of these records is unproven; this is a separate acceptance check, not a claim of a found cross-runtime attack.

### 5.10. What to lay down for V2 and what not to do now

Needed now: durable identity/principal IDs, a versioned signed envelope, critical/noncritical extension policy, scoped grants, stable operation IDs, generic typed payload and the separation of a factual receipt from a subjective statement. A future order ID can be a new application payload; the payment contract and reputation must have separate types/authority rules. A delivery receipt does not become proof of the performer's work quality.

Not needed before the messenger release: agent marketplace discovery, A2A conformance, escrow/order lifecycle, reputation aggregation, job rooms and a mass DeFi model. They are already deferred by scope. Isolating the current `core/jobs.rs`/JobsPanel/tools is relatively cheap because the common identity/capability/message foundations remain. Keeping readers for historical V2 payloads and regression tests is cheaper than making V1 depend on further jobs development.

One cannot, however, call transport custody payout «V2 DeFi» and quietly cross it out: L03–L05, funded onboarding and the organization share are still mandatory in V1. Deferring them is a separate change of the economic promise, not a consequence of the already adopted decision to defer orders.

## 6. The next five finished user stages

The estimates are relative: M — local integration of several existing parts; L — an end-to-end lifecycle with failures; XL — several coupled lifecycles/platforms. These are not deadlines and not a promise of a calendar plan. The stages describe outcomes and do not require sequentially blocking all independent teams.

| Stage | What the user gets | Parts and dependencies | Verifiable outcome/E2E | Relative effort |
| --- | --- | --- | --- | --- |
| **1. A long conversation without an issuer reset** | The paid service does not end on a short run; the queue frees up, an authority change and an L2 outage have an understandable outcome, old paid retrieval is not lost | F04/P01/P03/P04/L06: durable queue, indexed spent set, bounded proofs, snapshots, handover, authority refresh, reservations. The basis is the existing Core/DM and the format of historical obligations | E20/E21 and parts of E01/E05: concurrent same ticket at different nodes, crash before/after commit/QC, several epochs and substantially >128 spends without a new issuer; terminal jobs free active capacity; a partition does not create two finalizations; after the lease new promises are stopped, old active ones are read | **XL**; a targeted lifecycle rework, not a replacement of the consensus engine |
| **2. A person and an agent manage without internal commands** | The book/budget are visible in the UI; a person and a scoped CLI/MCP send messages, get honest statuses and continue after a restart | A common daemon service, messenger CLI/skill, wallet UI and a single read model; a default build without the new prover. Long paid tests use the stage 1 lifecycle | E01/E11/E14 parts: install/open profile, purchase/activate a testnet book without owner IPC, send via UI and CLI independently of MCP, a revoked queued runtime does not send, an SQL failure gives no success; load does not block the local UI/network | **L**; UI/CLI and the Windows adapter can be prepared in parallel with stage 1 |
| **3. | **4. A group and device loss do not destroy communication** | Groups/bounded participants, device revocation, the return of an offline participant and an understandable profile/history recovery | I03/I05/I06, G01–G06, U03/U05: encrypted control ordering, payload availability, epoch-aware catch-up, backup/rejoin, migration. | **5. The full acceptance criterion does not end with a successful happy path. For every stage at least the following are also needed: a cold restart in an intermediate state, duplicate replay, an unavailable dependency, quota exhaustion and proof of the absence of false success. New independent oracles must verify the user's outcome, not reproduce the Work.view structure from production code.

### 6.1. Decisions the owner must make

**Recommended narrow preview:** keep key-only identity, real P2P/MLS, DM and basic groups, scoped CLI/MCP, paid or sponsored testnet books, bounded durable storage with R10, offline recovery and safe profile restoration. First of all reduce provider diversity: do not build Google, Telegram, website/org attestors and all multi-provider credit issuance at the same time before this result. A new scope revision must explicitly list which O/L/G subtasks and E2E are deferred.

The tradeoff of this decision: the user may need an invite and an already funded/sponsored testnet book; there is no promise of universal free social-login onboarding and provider-neutral dedup claims. If payout/royalty is deferred — operators act on external sponsorship/voluntarily; the network is not yet declared economically self-sustaining. This is not a central message server, but a real operational dependence on sponsored resources.

I do not recommend silently removing R10, offline/history restoration or key recovery for the preview, or replacing groups with a permanent single vendor sequencer. That changes the core of the promised product. Reducing to one group privacy mode also requires describing the visible metadata and fanout cost; this is a separate product concession, not an implementation detail.

Three platforms remain mandatory. A mac-only preview release is possible only by a new owner decision; the current explicit Windows stub cannot be renamed to «not enough tests». Operator independence, the economic reserve/TTL and the guarantee for losing the last device also require explicit wording, not the marketing «everything is restored».

**Without such a decision the original 67 cards and 22 E2E apply.** The section 4 matrices are not re-scored for the proposed preview and do not reduce the debt unnoticed.

### 7.4. Clean build, environment and operation

`build-storage.py check` without the private `.local/build-storage.json` does not require the historical `/Volumes/...`; it would be wrong to accuse the archive of a mandatory dependence on the author's disk. However, `build-desktop.mjs` is oriented at the current host, shell tooling and `.app`, copies binaries from an assumed `target` path and unconditionally runs the legacy proof build. There is a minimum Rust version and locked dependencies, but pinned toolchains/Node and all native clean environments are not shown as a finished release mechanism.

A practical set of fixes: documented/pinned toolchains; a V1 target without the prover; separate legacy regressions; obtaining target paths from build metadata instead of assumptions; platform-specific installer/signing; Unix/Windows IPC parity; encrypted schema migration; rollback-safe backup; bounded disk/history/queue retention; operator diagnostics and a reproducible current revision gate. Voluntary updates must not give the company the right to stop old paid retrieval or forcibly change the trust profile.

Diagnostics must make it possible to understand who exactly is not answering: bootstrap, relay, checkpoint quorum, spend committee, storage quorum, index range or recipient. Stable error codes, correlation of operation/ticket IDs without plaintext and private keys, visible expiry/lease and repair reserve state are needed. A single «network error» leads to unreasonable retries and double reservation. The current bounded errors/fences are a useful foundation, but a whole operator/user diagnostics and resource SLOs are unproven.

### 7.5. Unknown parameters and what would change the conclusion

Not established: the expected size of the active network and of messages per issuer; the average/maximum ciphertext and attachment workload; WAN RTT/loss; the number of truly independent operators and the correlation of storage failures; the attacker's capital share/cost and grinding; the number/geography/administrators of checkpoint keys; the chosen L2/finality policy and the outage lease duration; the actual price of resources and the reward/repair reserve; the share of unspent legacy books; the recovery requirement after losing all device secrets; user p95/p99 and the acceptable storage cost; the cold build cost on three OSes.

The conclusion about the need for a targeted rework could be changed by verifiable data: an alternative actually connected path that continues the same issuer past 128 and handover without a reset; a working network index with book/epoch completeness; a real autonomous R10 without the owner; an independent company-off deployment; working CLI/wallet/groups/backup/Windows on **this** snapshot. A low-level function, a separate successful receipt and a reference to planned work are not such data.

Measured low load may reduce the urgency of some optimizations but does not remove the hard lifetime limits, the missing mandatory platform and the non-working recovery. Conversely, a large planned agent load would raise the priority of indexed state/scheduling even before further expansion of the economy.
